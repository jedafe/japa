# ADR-047: Admin Impersonation — Audit-First Session Design

**Status:** Accepted

**Context:** Support staff regularly need to reproduce issues reported by users — broken UI states, permission edge cases, locale-specific rendering bugs. Without impersonation, support requires users to share screenshots or screenshare, which is slow and often inconclusive. The feature is standard in platforms of this type (Stripe, Intercom, Zendesk all have it). The risk is misuse: an admin viewing private data or performing actions without the user's knowledge.

**Decision:** Valkey-backed impersonation sessions (`jc:impersonate:{admin_id}` → `{target_user_id}`, 30-minute non-renewable TTL) with mandatory audit logging on every session start, accidental overlap, and end. The `audit_logs` table (Section 21) gains an `impersonated_user_id` column so that every action performed during a session is permanently linked to both the real admin (`actor_user_id`) and the target (`impersonated_user_id`). Gated by the `admin.impersonate` permission node, not granted to any default role including `super_admin`. Admin-on-admin impersonation is forbidden at the handler level.

**Rationale:** Valkey TTL provides an automatic session cleanup that doesn't depend on the admin remembering to end the session. Keeping the real admin identity in context (separate context key from the effective user ID) means audit logging never loses the true actor even if downstream handlers only look at the effective user. The non-renewable TTL is intentional — it forces re-initiation for extended sessions, creating an additional audit trail entry and a natural pause. The 30-minute window is long enough for a typical support investigation and short enough to limit damage from a forgotten session.

**Consequences:** `audit_logs` requires a migration to add `impersonated_user_id`. The impersonation middleware must run after auth but before all route handlers. Support for impersonation in the Admin Panel query interface (filter audit logs by `impersonated_user_id IS NOT NULL`) is required at launch — otherwise the audit trail is write-only and not operationally useful. The no-admin-on-admin rule must be enforced at the API layer, not just the UI; UI enforcement alone is not sufficient.
