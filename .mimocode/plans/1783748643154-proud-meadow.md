### 1.1 BE-033: Fix `admin_broadcasts` INSERT column mismatch

**File:** `internal/admin/moderation.go` (lines 443-446)

**Bug:** The INSERT uses columns `(tenant_id, sender_id, subject, body, recipient_count, created_at)` but the migration `000119_missing_moderation_tables.up.sql` defines the table as `(id, title, body, sent_by, sent_at, recipient_count)` — no `tenant_id` column.

**Fix:** Update the INSERT to match migration columns:
```go
_, err = tx.Exec(ctx, `
    INSERT INTO admin_broadcasts (title, body, sent_by, recipient_count, sent_at)
    VALUES ($1, $2, $3, $4, now())
`, title, body, senderID, len(userIDs))
```
- Remove `tenant_id` (not in schema)
- `sender_id` → `sent_by`
- `subject` → `title`
- `created_at` → `sent_at`

Also update `ListBroadcasts` (line 766) — the SELECT already uses correct column names (`sent_by`, `title`, `sent_at`), so no change needed there.

### 1.4 BE-041: Implement permission cache invalidation for ban/unban

**Problem:** AGENTS.md Rule 6 mandates calling `InvalidatePermCache` after `user_bans` insert. The `BanUser` handler inserts into `user_moderation_actions` but does NOT invalidate the permission cache. The ban enforcement middleware caches "not banned" state in `jc:perm:{user_id}`, so after banning, the user retains access for up to 5 minutes.

**Existing infrastructure:**
- `rbac.InvalidateUserCache(ctx, userID)` in `internal/rbac/rbac.go:258` — does exactly what's needed
- `rbac.InvalidateAllCache(ctx)` in `internal/rbac/rbac.go:276` — for full flush
- `control.FlushCache` handler at `internal/control/handlers.go:508` — currently a 501 stub

**Approach:**
1. Add a standalone `InvalidatePermCache` function to `internal/rbac/rbac.go` that wraps `InvalidateUserCache` with the signature from section 03 (`func InvalidatePermCache(ctx context.Context, v *valkey.Client, userID pgtype.UUID) error`)
2. Add RBAC resolver and Valkey client dependencies to `admin.Handlers` struct (in `internal/admin/settings.go`)
3. Call `InvalidatePermCache` after `BanUser` and `UnbanUser` operations in `internal/admin/moderation.go`
4. Implement the `FlushCache` control handler using `rbac.InvalidateAllCache`

**Files to modify:**
- `internal/rbac/rbac.go` — add `InvalidatePermCache` wrapper
- `internal/admin/settings.go` — add RBAC/Valkey fields to Handlers struct
- `internal/admin/moderation.go` — call invalidation after ban/unban
- `internal/server/server.go` — pass RBAC/Valkey to admin.NewHandlers
- `internal/control/handlers.go` — implement FlushCache

### 1.5 BE-042: Fix impersonation audit-log failure handling

**File:** `internal/impersonation/service.go` (lines 46-63)

**Bug:** `EndImpersonation` logs a warning on audit-log failure but returns nil. This creates an audit gap — the impersonation ended but there's no record.

**Fix:** Return the audit-log error from `EndImpersonation`. The caller (handler) should return HTTP 500 on failure. The state is already cleared, but the audit gap is a compliance issue per Rule 10. The handler should log the error and return HTTP 500 so the admin knows the audit trail is incomplete.

### 1.6 BE-043: Implement FlushCache control handler

**File:** `internal/control/handlers.go` (lines 508-512)

**Bug:** Returns 501 Not Implemented. Routes exist, RBAC has `InvalidateAllCache`.

**Fix:** Implement using the RBAC resolver:
```go
func (h *Handlers) FlushCache(w http.ResponseWriter, r *http.Request) {
    if h.RBAC == nil {
        writeError(w, http.StatusServiceUnavailable, "rbac_unavailable", "RBAC not configured")
        return
    }
    h.RBAC.InvalidateAllCache(r.Context())
    writeJSON(w, http.StatusOK, map[string]any{
        "data": map[string]any{"message": "Permission cache flushed"},
    })
}
```
- Add `RBAC *rbac.RBAC` field to `control.Handlers` struct
- Pass it from server.go during construction

## Part 2: Bits UI Adoption in Main App

### Current State
- `bits-ui: ^2.18.1` installed in `apps/main/package.json`
- Only 3 files use bits-ui (all `DropdownMenu`): Header.svelte, SpaceSwitcher.svelte, NotificationCenter.svelte
- `$lib/components/ui/` has only 3 components (EmptyState, ErrorState, LoadingSkeleton) — none use bits-ui
- 200+ raw `<button>` elements, 90+ raw `<input>` elements, 16 `<select>`, 16 `<textarea>` across 60+ files
- learn/docs apps have wrapper components (Button, Input, Badge, Card, Spinner) but only Button wraps a bits-ui primitive

### 2.1 Create Bits UI wrapper components in main app

Create `$lib/components/ui/` wrappers that match the learn/docs pattern but properly use bits-ui primitives:

| Component | File | bits-ui primitive |
|-----------|------|-------------------|
| Button | `Button.svelte` | `Button.Root` from bits-ui |
| Input | `Input.svelte` | Raw `<input>` with consistent styling (bits-ui doesn't have Input) |
| Badge | `Badge.svelte` | Raw `<span>` with variant classes |
| Card | `Card.svelte` | Raw `<div>` with consistent styling |
| Spinner | `Spinner.svelte` | Raw SVG with size variants |
| Select | `Select.svelte` | `Select.Root` from bits-ui |
| Textarea | `Textarea.svelte` | Raw `<textarea>` with consistent styling |
| Dialog/Modal | `Modal.svelte` | `Dialog.Root` from bits-ui |

Update `$lib/components/ui/index.ts` to export all new components.

### 2.2 Migrate highest-impact pages

Migrate the pages with the most raw form elements to use the new wrappers:

1. **`/settings`** — 4 inputs, 6 buttons, 1 textarea → Button, Input, Textarea
2. **`/settings/security`** — 2 inputs, 6 buttons → Button, Input
3. **`/settings/notifications`** — 3 inputs → Input
4. **`/login`** — 2 inputs → Input
5. **`/register`** — 3 inputs → Input
6. **`/forgot-password`** — 1 input → Input
7. **`/reset-password`** — 2 inputs → Input
8. **`/checkout`** — 1 input, 7 buttons → Button, Input
9. **`/pricing`** — 1 input, 8 buttons → Button, Input

**Strategy:** Migrate imports and class names only — do NOT change behavior or layout. The wrappers provide consistent styling and accessibility without breaking existing functionality.
